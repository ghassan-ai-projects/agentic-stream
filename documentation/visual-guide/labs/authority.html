Lab 4 · Governance and effect planes

A proposal is not permission, and "OK" is not proof

Send a proposed action down the real path: validator, policy, outbox and dispatch, device, verification. Flip the conditions of the world and watch where it stops, what record is written, and what a lost reply does.

Reading the picture

Gates, records, outcome

Each gate either passes the proposal or stops it and writes a durable record with a reason. The chips under the picture are those records, in order.

Key idea

Check again, right before acting

Policy is evaluated against current state at dispatch. A superseded intent is marked stale, an engaged operator stop is denied, and a runtime that lost ownership is fenced from writing.

Why it matters

Unknown is a real answer

If a reply is lost, the system records an unknown outcome and reconciles with evidence. A stable idempotency key lets a provider that honours it recognise a repeat as the same request. A command with nothing to read back ends in manual review, and a refused command closes its verification as refuted.

Words used here

Outbox
A durable record written before a command is sent, so a crash cannot lose it and a retry finds it.
Fence
A number that rises with each owner of the runtime. A write from an older owner carries a stale number and is refused.
Idempotency key
A stable id on a command. A provider that honours it treats a repeat as the same request.
Receipt, result, query_state
The three answers: the device accepted it, the device says what happened, and a separate read of the output's state.
Refuted, manual review
Refuted: the command was refused or failed, so no effect exists to verify. Manual review: the outcome is unknown and nothing could ever be read back, so a person decides.
The gate order, the risk classes (R0, R1, R2), the human approval rule for R2, and the three answers (receipt, result, query_state) follow the design and the recorded run.
